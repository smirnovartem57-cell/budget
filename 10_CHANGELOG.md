## 2026-07-25 — «Кредиты × Цели»: стратегия погашения и очередь приоритетных кредитов

**Схема БД**: `credits.goal_payoff_strategy` (`close_before_goal`/`scheduled_during_goal`, по
умолчанию `close_before_goal`), `credits.goal_priority_order` (ручной приоритет очереди,
nullable), `credits.allow_extra_payment_before_goal` (по умолчанию `true`) — уже применены к
живой базе на предыдущем шаге, миграции сохранены в `supabase/migrations/` (идемпотентны,
`add column if not exists`). Backfill по `credit_type` (ипотека → `scheduled_during_goal`,
остальные → `close_before_goal`) тоже сохранён как файл, с защитой от повторного деструктивного
запуска (WHERE ограничивает повтор строками, ещё не отредактированными вручную). Добавлена новая
миграция `financial_goals.debt_first_strategy` (default `true`) и
`pre_debt_goal_allocation_percent` (numeric 0–30, CHECK, default `0`).

**Известный нюанс данных**: запись «Ипотека» в реальной базе имеет `credit_type = consumer` (не
`mortgage`), поэтому backfill отнёс её к `close_before_goal`. `credit_type` этой записи не
переклассифицируется по названию автоматически — ни при backfill, ни в форме, ни при расчёте
прогноза (`calculateGoalForecast` берёт `goal_payoff_strategy` из сохранённого поля, не выводит
его из типа при каждом расчёте). Исправление стратегии для неё — ручное действие через форму
кредита («Выплачивать параллельно»), проверено сквозным тестом (см. ниже).

**Очередь погашения** (`getGoalPayoffQueue`, единственная функция построения очереди): активные
кредиты с `include_in_goal_forecast=true` и `goal_payoff_strategy=close_before_goal`,
отсортированные по `goal_priority_order` (если задан — имеет приоритет), затем просрочка, затем
тип (карта → потребительский → другое → авто → рассрочка), затем ставка по убыванию, остаток по
возрастанию, ближайшая дата платежа. Кредиты `scheduled_during_goal` (`getGoalParallelCredits`) в
очередь не входят и не блокируют старт накопления.

**Помесячная симуляция** (`simulateGoalPayoffMonths`, горизонт 240 месяцев, локальные копии
остатков — реальные строки `credits` не меняются): каждый месяц — минимальные платежи по всем
активным кредитам с процентами (`interestPart = remaining × ставка/12`, при отсутствии ставки
`interestPart = 0`), допресурс сценария делится между целью (`pre_debt_goal_allocation_percent`)
и первым незакрытым кредитом очереди; излишек, оставшийся после закрытия кредита в том же месяце,
каскадом уходит следующему в очереди, а если очередь пуста — в цель. После полного закрытия
очереди весь ресурс сценария идёт в цель. `payment_already_counted_in_mandatory=true` защищает от
двойного счёта — платёж не вычитается из потока отдельно, но кредит всё равно амортизируется и
может получать допплатёж. Возвращает обе даты (`priorityDebtsClosedMonth`/`goalReachedMonth`),
таймлайн, события закрытия кредитов и предупреждения (недостижимость в горизонте, платёж не
покрывает проценты).

**Форма кредита**: три опции вместо старого чекбокса — «Закрыть до накопления» / «Выплачивать
параллельно» / «Не учитывать» (маппятся в `goal_payoff_strategy` + `include_in_goal_forecast`);
«Разрешить досрочное погашение» показывается только для «Закрыть до накопления». При СОЗДАНИИ
кредита выбор типа «Ипотека» подсказывает параллельный режим — но это не переопределяет
сохранённый выбор при РЕДАКТИРОВАНИИ (`state.editingCreditId` проверяется явно). «Не учитывать»
не перезаписывает `goal_payoff_strategy` в БД (поле просто не входит в payload), чтобы стратегия
не терялась при повторном включении кредита в цель.

**Экран цели**: «План достижения цели» (этапы: закрыть очередь → начать копить → собрать сумму,
или «можно копить уже сейчас», если очереди нет), «Что закрываем перед автомобилем» (очередь с
кнопками Выше/Ниже — пересчитывает и сохраняет `goal_priority_order` для всей очереди, не трогает
остатки кредитов), «Выплачиваются параллельно» (ипотека и подобные — с пометкой «не блокирует
цель»), карточки сценариев с двумя датами (закрытие очереди + цель) вместо одной, главная
карточка цели и компактный виджет на главной — строка «сначала кредиты: до …» либо «ипотека не
блокирует цель». Под графиком сценариев — текстовые метки ключевых дат (плагин аннотаций Chart.js
недоступен из песочницы, как и в этапе 2 — CDN заблокирован политикой egress).

**Тестирование**: юнит-тесты (Node, код извлечён дословно из `index.html`, не копия) — очередь
«только ипотека» (пустая очередь, накопление сразу, ипотека не в приоритете), «карта +
потребительский + ипотека» (порядок очереди, ипотека вне очереди), двойной счёт
(`payment_already_counted_in_mandatory` true/false), распределение 0/10/20/30%
(`goalContribution + extraDebtPayment === strategyAllocation` точно), ручная перестановка
(`goal_priority_order` переопределяет автоматику, остатки кредитов не меняются), формула
процентов, кредит без ставки — 37/37 пройдено. Сквозной браузерный тест (headless Chromium,
реальный код приложения, заглушки Supabase/Chart.js/lucide — CDN недоступен из песочницы):
форма кредита показывает реально сохранённую стратегию для записи «Ипотека» (не выводит её из
названия/типа), ручное переключение в «Выплачивать параллельно» сохраняется и убирает кредит из
очереди при этом сохраняя его платёж среди параллельных, перестановка очереди сохраняет
`goal_priority_order` — 13/13 пройдено, посторонних ошибок консоли не обнаружено.

**Не менялось**: расчёт свободного остатка (доход/обязательные/переменные расходы), раздел
«Долги», реальные суммы существующих кредитов (backfill не менял `remaining_amount` и т.п.),
баланс, аналитика, календарь проверки расходов, доходы, покупки, подписки, нижняя навигация.

## 2026-07-25 — Раздел «Цели» (этап 2): прогноз накопления

**Новый раздел** для накопления на крупную покупку — на этом этапе тип цели один
(«Автомобиль»), схема БД (`goal_type` без CHECK-ограничения) архитектурно допускает другие
значения в будущем без миграции, интерфейс просто не предлагает их сейчас. Таблица
`financial_goals` с RLS `auth.uid() = user_id` на SELECT/INSERT/UPDATE/DELETE.

**Расчёт прогноза** (`calculateGoalForecast`, единая функция для «живой» карточки цели и
`simulateGoalScenario` без сохранения): свободный остаток = доход − обязательные расходы −
переменные расходы − платежи по кредитам (если включено). «Обязательные» расходы — те же
данные, что и в «Ближайшие платежи» (§11 прошлого ТЗ): шаблоны активных регулярных расходов +
подписки, а не историческое усреднение — так исключён двойной счёт с переменными расходами
(средними за 3/6/12 завершённых месяцев, настраивается). Каждое из трёх полей можно заменить
своим значением (`monthly_*_override`). Три сценария — комфортный/базовый/ускоренный (проценты
свободного остатка, направляемые на цель, по умолчанию 50/70/90%) — дают срок и дату
достижения цели. Кредиты учитываются только если отмечены «Учитывать кредит при расчёте
финансовых целей» в разделе «Кредиты» и ещё не отмечены как уже учтённые в обязательных
расходах — `payment_already_counted_in_mandatory` защищает от двойного счёта (заложено этапом 1
«Кредитов»).

**Экран `goalsView`**: карточка цели (прогресс, отложено/цель/осталось, статус, сравнение с
желаемой датой), три карточки сценариев + горизонтальный bar-график (Chart.js, месяцев до
цели), разбивка свободного остатка по строкам, влияние кредитов (список учтённых кредитов),
форма настроек (переиспользуется для создания и редактирования, как у «Кредитов»). Вход — тот
же паттерн, что у «Кредитов»/«Аналитики»: верхняя вкладка на десктопе (7-я, укладывается в
1040px без переполнения), без кнопки в нижней навигации, карточка «Цели» на главной с прогрессом
и сроком по базовому сценарию.

**Тестирование**: 8 сценариев расчёта юнит-протестированы в изоляции (Node) — базовый случай,
отключение кредитов, ручные переопределения, цель уже достигнута (0 месяцев), недостижимый
свободный остаток (0 — сценарий помечается «Недостижимо»), сравнение с желаемой датой. Полный
экран (hero → сценарии → разбивка → влияние кредитов → настройки, включая заполнение формы
редактирования и мобильную раскладку) прогнан в headless Chromium против реального кода
приложения с тестовыми заглушками Supabase/Chart.js/lucide (CDN этих библиотек недоступен из
песочницы — заблокирован политикой egress) — 0 ошибок в консоли, все посчитанные значения
совпали с юнит-тестами.

**Не менялось**: раздел «Долги», раздел «Кредиты» (кроме уже заложенных в этапе 1
`include_in_goal_forecast`/`payment_already_counted_in_mandatory`), баланс, аналитика,
календарь проверки расходов, доходы, расходы, подписки, покупки, нижняя навигация.

## 2026-07-25 — Отдельный раздел «Кредиты» (этап 1)

**Новый раздел**, отдельный от существующих личных «Долгов» (люди/займы, таблица `debts`).
«Кредиты» — банковские обязательства: ипотека, потребительские кредиты, автокредиты, рассрочки,
кредитные карты. Данные не пересекаются: `debts` не трогали, новые таблицы `credits` и
`credit_payments` с RLS `auth.uid() = user_id` на SELECT/INSERT/UPDATE/DELETE.

**Вход в раздел** — тот же паттерн, что у «Аналитики»: без новой постоянной кнопки в нижней
навигации (мобильный таббар не перегружен), верхняя вкладка `.page-tabs` на десктопе (6 вкладок
без переполнения на 1024px+) и компактная карточка «Кредиты» на главной с кнопкой «Подробнее» —
отдельно от карточки «Долги».

**Экран `creditsView`**: 4 KPI (осталось выплатить / платежи в месяц / ближайший платёж /
активных кредитов, единая функция `calculateCreditSummary()`), форма добавления (переиспользуется
для редактирования через `state.editingCreditId`), фильтры Активные/Погашенные/Все, карточки
кредитов с типом/цветом/прогрессом погашения. Detail-экран — модальный лист (общий DOM для
мобильного и десктопа) с историей платежей, действиями «Отметить платёж»/«Редактировать»/«Закрыть
кредит»/«Удалить».

**Против двойного учёта**: `payment_already_counted_in_mandatory` — платёж кредита, уже внесённый
в обязательные расходы, не попадает в `monthlyPaymentsNotAlreadyCounted` (используется будущим
этапом расчёта цели, не KPI «Платежи в месяц» — это фактическая кредитная нагрузка). Отметка
платежа кредита **не создаёт** операцию расхода автоматически и **не меняет** текущий остаток
семьи — только обновляет данные самого кредита (остаток, следующая дата платежа через безопасный
перенос на месяц вперёд с зажимом по длине месяца: 31 января → 28 февраля).

**Не менялось**: формула текущего остатка, baseline операций, ручные сверки, категории,
аналитика, календарь проверки расходов, доходы, обычные расходы, подписки, обязательные расходы,
покупки, нижняя навигация, `Europe/Moscow`, раздел «Долги».

## 2026-07-25 — Постоянный статус повторной проверки и массовые регулярные расходы

**Проблема:** «Требует повторной проверки» существовал только в сессионном `state.dayChecksInvalidatedLocally`
(терялся при перезагрузке/повторном входе), а инвалидация мутацией расхода физически удаляла
строку `expense_day_checks` — «постоянного» статуса не было в принципе. Массовые операции над
регулярной серией (`deleteRecurringGroup`, `updateRecurringGroupDate`) вообще не трогали календарь.

**Модель:** `expense_day_checks` получила `invalidated_at timestamptz` и `invalidation_reason text`
(nullable). Строка теперь НЕ удаляется при инвалидации — только помечается. Статус дня:
нет строки → «не проверен»; строка, `invalidated_at IS NULL` → «проверен»; строка,
`invalidated_at IS NOT NULL` → «требует повторной проверки» — persist, переживает перезагрузку и
повторный вход. Единственное исключение — ручное «Снять отметку» по-прежнему удаляет строку
целиком (это осознанное действие пользователя, а не побочный эффект мутации).

**Единая пакетная функция** `invalidateExpenseDayChecks(dates, reason)` заменила прежний
`invalidateExpenseDayCheck(date)` (по одному DELETE на дату). Принимает строку/массив/`Set`,
нормализует и дедуплицирует даты, обновляет их ОДНИМ `UPDATE ... WHERE user_id=... AND
check_date IN (...) AND invalidated_at IS NULL` — трогает только уже отмеченные дни, для
непроверенных дней строка не создаётся. Причины: `expense_created`, `expense_updated`,
`expense_deleted`, `expense_date_changed`, `recurring_group_deleted`, `recurring_group_updated`,
`shopping_expense_created`.

**Повторное подтверждение** (`confirmExpenseDay`) переведено с INSERT+перехват конфликта 23505
на единый `UPSERT` по `(user_id, check_date)`, всегда обнуляющий `invalidated_at`/`invalidation_reason`
и обновляющий `checked_at`/`updated_at` — раньше конфликт 23505 просто читал существующую (всё ещё
инвалидированную) строку, не снимая статус.

**Массовые операции над регулярной серией** — единственные существующие в кодовой базе такие
функции (`deleteRecurringGroup`, `updateRecurringGroupDate`; отдельных функций массового изменения
суммы/категории/названия серии не найдено — не над чем было проводить эту доработку) теперь
собирают затронутые даты РАСХОДНЫХ операций до/после изменения и инвалидируют объединение одним
пакетным запросом. Дубли дат (несколько операций в один день) дедуплицируются автоматически.

**Не изменилось:** формула остатка, RLS-политики (UPDATE-политика уже была per-row, не per-column
— новые колонки под неё не потребовали правок), доходы по-прежнему не трогают календарь расходов,
разметка календаря, часовой пояс Europe/Moscow.

## 2026-07-25 — Единая часовая зона приложения: Europe/Moscow (UTC+3)

**Срочная корректировка.** До этого раунда в приложении сосуществовали три независимых
источника «текущей календарной даты»: UTC (`todayStr()` через `new Date().toISOString()`),
`Asia/Almaty` (`BALANCE_TIMEZONE`/`localSnapshotDateStr()` для сверок и календаря расходов) и
неконтролируемый локальный часовой пояс устройства пользователя (`daysSinceTs()` через
`.getFullYear()/.getMonth()/.getDate()`). Около полуночи это создавало риск, что операция,
сверка или отметка календаря попадут не на тот день.

**Новое единое правило:** одна константа `APP_TIMEZONE = 'Europe/Moscow'` и одна функция
`appTodayStr()` (через `Intl.DateTimeFormat` с явным `timeZone`) — единственный источник
календарной даты для всего приложения. `todayStr()`, `localSnapshotDateStr()`,
`calendarTodayStr()` оставлены как имена-делегаты к `appTodayStr()` (не отдельные реализации),
чтобы не переименовывать десятки существующих вызовов по файлу.

**Затронуто:** `hasHappened()` (свершившаяся операция), `snapshot_date` новой/сегодняшней
сверки, статусы календаря проверки расходов (сегодня/прошлое/будущее), дата новой операции по
умолчанию (расход/доход/повтор/«сохранить и добавить ещё»/из календаря), `daysSinceTs()`
(«Подтверждено N дней назад» — по календарным дням, не миллисекундам), отображение времени
(`toLocaleTimeString` с явным `timeZone`), два расчёта «сегодняшнего» дня месяца на графиках
(`.getDate()-1` → на основе `appTodayStr()`), а также два попутно найденных бага в
«Ежемесячные расходы» (`renderRecurring`/`renderRecurringDueSoon`): 7-дневный горизонт считался
через рассинхронизированную местную/UTC арифметику, а нижняя и верхняя граница окна вообще
использовали разные способы расчёта.

**Хранение в БД не менялось** — `timestamptz`-поля (`created_at`, `updated_at`, `checked_at`)
остаются в UTC; поменялась только пользовательская календарная ИНТЕРПРЕТАЦИЯ дат. Проверка
`balance_snapshots.snapshot_date` (аудит по `(created_at at time zone 'Europe/Moscow')::date`)
и перепроверка baseline (`operations_income_baseline`/`operations_expense_baseline` против
операций на московскую дату снимка) — обе выполнены агрегатными запросами (без вывода сумм);
расхождений не найдено (`mismatches=0`), миграция данных не потребовалась.

**Не менялось:** суммы операций, категории, формула текущего остатка, RLS, аналитика, история
сверок, разметка календаря, Долги/Покупки/Подписки/Бюджет, импорт.

## 2026-07-24 — Автоматическое изменение общего остатка после операций

**Отменяет прежнее правило** «добавление расхода не изменяет реальный остаток» (см. записи
ниже — «Календарь проверки...» и «Ускорение внесения расхода» в части утверждений о неизменности
остатка: они описывали поведение ДО этого раунда). Новое правило: последняя ручная сверка —
подтверждённая базовая точка; текущий показатель на главной — это сверка ± операции,
добавленные/изменённые после неё.

**Два понятия, оба сохраняются отдельно:**
- Подтверждённый остаток — то, что пользователь вручную ввёл при последней сверке
  (`balance_snapshots.net_balance`), историческая точка, не переписывается.
- Текущий остаток — подтверждённый ± изменения операций после сверки; теперь это главная
  сумма карточки («Текущий остаток семьи», было «Реальный остаток семьи»).

**Миграция:** `balance_snapshots` получила два новых поля — `operations_income_baseline` и
`operations_expense_baseline` (numeric, nullable). Формула ТЗ (`operations_balance_baseline =
доходы − расходы`) не изменилась — просто хранится в двух слагаемых, а не одним комбинированным
числом, потому что разбивка «Доходы после сверки» / «Расходы после сверки» на главной обязана
считаться ОТНОСИТЕЛЬНО baseline (не простым фильтром по дате, иначе перенос/правка/забытая задним
числом операция считались бы неверно) — одно комбинированное число такую разбивку не
восстановит. Безопасная разовая инициализация: для ПОСЛЕДНЕЙ сверки каждого пользователя baseline
= фактический итог операций на момент миграции — `operations_delta` сразу после неё равен нулю,
отображаемая сумма не изменилась.

**Формула** (`calculateCurrentFamilyBalance()` — единственное место, где она считается):
```
currentBalance = confirmedBalance + incomeDelta + expenseDelta
incomeDelta  = текущий доход (hasHappened) − operations_income_baseline
expenseDelta = −(текущий расход (hasHappened) − operations_expense_baseline)
```
Устойчиво к правкам задним числом, переносу дат, редактированию и удалению старых операций —
пересчитывается от общего итога, а не диапазоном дат после сверки.

**Сохранение сверки** (`saveBalanceSnapshot`) — и создание, и правка сегодняшней записи всегда
пересчитывают baseline заново из уже загруженных `state.transactions`, обнуляя накопленное
изменение. Сама сверка (`net_balance`, форма) не пересчитывается по операциям — остаётся вводом
пользователя, как и раньше.

**Карточка на главной** — заголовок «Текущий остаток семьи»; подпись — «Сверено сегодня в HH:MM»,
пока со сверки ничего не изменилось, иначе «На основе сверки от {дата} и внесённых операций»; для
сверки старше 7 дней — «Расчётный остаток на основе сверки N дней назад» (не называется полностью
подтверждённой, без красного цвета). Расшифровка — разбивка по долгам (если есть) плюс
«Подтверждено вручную / Доходы после сверки / Расходы после сверки / Текущий остаток», когда
что-то изменилось.

**Без ручной сверки** — прежнее пустое состояние («Укажите реальный остаток») не изменилось;
расчёт по операциям без сверки не выполняется.

**Отсутствующий baseline** (переходный случай) — временно показывается подтверждённый
`net_balance` (не 0, не ошибочный пересчёт), тихая одноразовая доинициализация
(`ensureBalanceBaseline`); при неудаче — нейтральная подпись «Не удалось учесть новые операции» +
«Повторить», остальное приложение работает.

**Не изменилось:** сама ручная сверка, история сверок и её график (по-прежнему только
подтверждённые `net_balance`), «Сверка операций» (расхождение между двумя подтверждёнными
сверками — сравнение уже строилось на подтверждённых снимках, код не тронут), аналитика категорий/графики,
календарь проверки расходов (снятие отметки при мутации расхода не связано с расчётом остатка —
оба обновляются из одного и того же `loadAll()`→`renderEverything()`, без дополнительных запросов).

**Проверено:** новый/повторённый/отредактированный/удалённый расход и доход корректно
двигают текущий остаток (в т.ч. только на разницу при правке, а не на новую сумму целиком);
«Сохранить и добавить ещё» — оба расхода уменьшают остаток; перенос операции между двумя
прошедшими датами без изменения суммы остаток не меняет; расход, добавленный задним числом уже
после сверки, всё равно уменьшает остаток; новая сверка обнуляет `operationsDelta`; история сверок
не переписывается.

## 2026-07-24 — Календарь проверки полноты расходов по дням

Новая, полностью отдельная от аналитики функция ручного контроля: пользователь сам отмечает
дни, за которые расходы точно внесены. Наличие операций НИКОГДА не переводит день в «Проверен»
автоматически — это единственное правило, вокруг которого построена вся фича. Суммы, категории,
графики, реальный остаток, доходы, долги, покупки, подписки и нижняя навигация не изменены.

**Новая таблица Supabase** `expense_day_checks` (`id`, `user_id` not null → `auth.users`,
`check_date` date, `checked_at`/`created_at`/`updated_at` timestamptz, `unique(user_id,
check_date)`). RLS включён, 4 политики — `expense_day_checks_select_own` /
`_insert_own` / `_update_own` / `_delete_own`, все вида `auth.uid() = user_id`. Анонимный режим
не читает и не пишет эту таблицу (демо — только локальные mock-данные, без записи).

**Локальная дата** — переиспользован уже существующий `localSnapshotDateStr()` (Asia/Almaty,
из раунда «Реальный остаток семьи») через новую тонкую обёртку `calendarTodayStr()`; нигде не
использован `toISOString().slice(0,10)` для определения текущего календарного дня.

**5 статусов дня** (`getDayStatus`): будущий (недоступен) → проверен (есть строка в
`expense_day_checks`) → требует повторной проверки (была строка, снята мутацией расхода **в
этой сессии** — простое, непостоянное клиентское состояние `state.dayChecksInvalidatedLocally`,
как и предполагает «простая реализация» ТЗ: после перезагрузки день просто станет обычным
непроверенным) → есть расходы, не проверен → нет расходов, не проверен.

**Снятие отметки при мутации расхода** (`invalidateExpenseDayCheck`, с одной повторной попыткой
и нейтральным тостом при неудаче — сохранённый расход никогда не откатывается) подключено во
все точки изменения расхода: создание через форму (`submitTxSheet`), правка через детальный
лист (`txDetailSaveBtn`, старая+новая дата при переносе), удаление (`deleteTx`), три инлайн-
правки в таблице «Операции» (`updateTxDate/Time/Amount`), дубликат операции
(`txDetailDuplicateBtn`), «Куплено» из списка покупок и его отмена. Доход нигде не снимает
отметку — ни один из этих вызовов не участвует в income-путях (`createIncomeTransaction`
и т.п.). Известное ограничение: массовые операции над серией регулярных расходов
(`deleteRecurringGroup`, `updateRecurringGroupDate`) пока не переоценивают отметки — не входят в
контрольный список ТЗ и оставлены как задокументированный пробел.

**Компактный блок на главной** «Проверка расходов» — сразу под «Последними операциями», семь
последних календарных дней (сегодня + 6), статус цветом+иконкой+aria-label, сводный текст (один
из 4 вариантов ТЗ, без тревожных формулировок), кнопка «Открыть календарь».

**Полный календарь** — один overlay `#expenseCalendarOverlay` с двумя панелями: сетка месяца и
панель дня. На мобильном день ЗАМЕНЯЕТ сетку (кнопка «Назад к календарю»), на ≥900px — обе
видны рядом (флекс-ряд, без дублирования DOM). Переход в будущие месяцы заблокирован. Второй
вход — иконка календаря рядом с фильтром на вкладке «Операции». Первое открытие показывает
одноразовую подсказку (localStorage).

**Панель дня** — сумма+количество (или «Расходов в приложении нет» без ложных заявлений),
статус-бейдж, список операций (только расходы, с существующими иконками категорий), «Добавить
расход» (открывает существующую форму `create-expense` с предзаполненной ТОЛЬКО датой — сумма/
категория/название/комментарий пустые, как раньше) и кнопка подтверждения с точным текстом под
ситуацию (сегодня / есть расходы / расходов нет). «Снять отметку» — без лишнего диалога
подтверждения. Конфликт уникальности (`23505`) при подтверждении — тихо подтягивает уже
существующую отметку и показывает день проверенным, без сырого текста Postgres. После
добавления/правки/удаления операции из панели дня, а также после закрытия детального листа,
пользователь возвращается на ту же панель дня (`state.calendarReturnDate`), календарь
пересчитывается без перезагрузки страницы.

**Побочный фикс:** z-index `.confirm-dialog-overlay`/`.action-menu-overlay` поднят с 1100 до
1200 — иначе более поздний в DOM модал (сам новый календарь) мог перекрыть уже открытый диалог
подтверждения удаления, блокируя клик. Пре-существующий баг, обнаруженный при тестировании этой
фичи, актуальный для любых будущих bottom-sheet модалов.

## 2026-07-24 — Одна сверка остатка в день + редактирование сегодняшней записи

Повторное открытие формы сверки в тот же локальный календарный день теперь редактирует уже
существующую сегодняшнюю запись вместо создания второй. Ежедневный учёт расходов/доходов,
категории, аналитика, история операций, долги, покупки не менялись.

- **Локальный календарный день — `Asia/Almaty`, не UTC.** Новая функция `localSnapshotDateStr()`
  (через `Intl.DateTimeFormat` с явным `timeZone`) — отдельная от существующей `todayStr()`
  (UTC-день, используется по всему проекту для дат операций и не тронута). Без этого разделения
  смещение до 5 часов после полуночи могло создать дубль или не дать сохранить сегодняшнюю сверку.
- **Режим формы — явное состояние**, а не вывод по тексту кнопки: `balanceFormMode` (`'create'` |
  `'edit-today'`) + `editingBalanceSnapshotId`. При открытии формы: если сверка за сегодня уже
  есть — режим `edit-today`, поля предзаполняются ИЗ НЕЁ (не из вчерашней), заголовок «Обновить
  сегодняшний остаток», подсказка про уже существующую сверку, нейтральная светло-синяя плашка
  «Сверка за сегодня уже сохранена», кнопка «Обновить сегодняшнюю сверку»; иначе — обычное
  создание с прежним поведением (заголовок/кнопка как раньше, автозаполнение из последней сверки).
- **Сохранение:** режим `edit-today` выполняет `UPDATE` существующей строки (суммы, `comment`,
  `updated_at`) — `id`/`user_id`/`created_at`/`snapshot_date`/`created_by` не трогаются; режим
  `create` выполняет обычный `INSERT` с `snapshot_date = localSnapshotDateStr()`.
- **Защита на уровне БД:** новый уникальный индекс `(user_id, snapshot_date)` — Postgres
  физически не даёт создать вторую сверку одного пользователя за один день (код ошибки `23505`).
  Конкурентное сохранение с двух устройств: клиент перехватывает `23505`, перечитывает сегодняшнюю
  запись, переключает форму в `edit-today` — без технического текста ошибки Supabase, без дублей.
- **Время последнего изменения:** добавлено поле `updated_at` (по умолчанию `now()`, обновляется
  при каждом `UPDATE`). Карточка и история показывают «Сверено сегодня в HH:MM» при первом
  сохранении и «Обновлено сегодня в HH:MM» после правки — использует `updated_at ?? created_at`.
  Расчёт актуальности остатка (3/7-дневные пороги) не менялся.
- **История и график** используют `snapshot_date` как источник календарного дня (не UTC-срез
  `created_at`) — одна строка/точка на день гарантирована уникальным индексом, отдельная
  клиентская дедупликация не понадобилась. Сегодняшняя запись подписана «Сегодня, сверено/
  обновлено в HH:MM».
- **Миграция данных:** бэкофилл `snapshot_date` из `(created_at AT TIME ZONE 'Asia/Almaty')::date`
  для существующей записи; проверка дублей по `(user_id, snapshot_date)` — в проде на момент
  миграции была ровно 1 запись, дублей не найдено, ничего не удалено (проверено количеством строк
  до/после миграции, без чтения самих сумм). SQL — `supabase/migrations/
  20260724_balance_snapshots_daily_uniqueness.sql`.
- RLS (доступ только `authenticated`, только к своим строкам) — без изменений, уже покрывает
  «анониму нельзя создавать/редактировать» и «нельзя обновить чужую запись» с прошлой доработки.

## 2026-07-24 — Доп. проверка «Реальный остаток семьи»: даты, RLS, целостность сумм

Повторная проверка функции реального остатка выявила и устранила 3 подтверждённых проблемы,
подтвердила отсутствие ещё двух (нет данных для их проявления) и задокументировала 2 сознательных
ограничения. Ежедневный учёт расходов/доходов не менялся.

**Подтверждено и исправлено:**
1. **Утечка будущих операций.** `sumTxRange()` не исключала операции с датой в будущем — операция
   с датой позже сегодняшней могла попасть и в «После последней сверки», и в расчёт расхождения
   между сверками. Добавлен фильтр `hasHappened(t)` (уже существующая в проекте конвенция,
   используемая везде в аналитике). Период по-прежнему считается по фактической дате операции
   (`t.date`), а не по дате внесения в приложение — так было изначально и осталось верно. Граница
   между сверками не менялась: предыдущая сверка не включается, текущая — включается.
2. **RLS `balance_snapshots` ужесточён.** Роль `anon` может только читать демо-строки
   (`user_id IS NULL`); `INSERT`/`UPDATE`/`DELETE` теперь разрешены только роли `authenticated` и
   только в свои строки (`auth.uid() = user_id`). Это отличается от остальных таблиц приложения
   (там демо-режим допускает анонимную запись) — сознательное исключение для этой таблицы из-за
   финансовой значимости данных. На клиенте `openBalanceSheet()`/`saveBalanceSnapshot()` для
   анонима теперь показывают «Войдите в аккаунт…» и открывают форму входа вместо тихого отказа.
   Миграция — `supabase/migrations/20260724_balance_snapshots_hardening.sql`.
3. **Целостность производных сумм.** Добавлен CHECK-constraint на уровне БД:
   `total_own_money = artem+oksana+cash+other` и `net_balance = total_own_money − credit_debt`.
   Выбран «Вариант B» (не «Вариант A» с отказом от хранения производных полей): в приложении и
   так единственная точка записи (`saveBalanceSnapshot`), а constraint гарантирует это и на
   уровне БД — без миграции существующих потребителей карточки/истории/графика на расчёт «на лету».

**Проверено, проблема не подтвердилась:**
- **Совместный доступ семьи.** В проекте одна общая учётная запись на всю семью (`usernames` —
  1 запись); привязка по `user_id` уже даёт Артёму и Оксане общий доступ к одному и тому же
  остатку и истории при входе под одной учётной записью. Отдельный `family_id` не требуется —
  не создавался.

**Сознательно не реализовано (задокументировано в коде и здесь):**
- **Переводы между своими картами.** В модели данных нет типа операции `transfer`
  (`transactions.kind` ограничен `income`/`expense` на уровне БД) — исключать нечего.
- **Двойной учёт при погашении кредитной карты.** Надёжно отличить «внутреннее погашение уже
  учтённого долга» от обычного расхода в текущей структуре категорий нельзя (категория «Кредит» —
  это выплаты по ипотеке/рассрочке, реальный расход, а не погашение карты) — автоматическое
  исключение не реализовано, чтобы не отфильтровать настоящие расходы по ошибке.

## 2026-07-15 — «Получен»: корректировка суммы + правила дублей

### Корректировка суммы при получении
- Кнопка «Получен» на ожидаемом доходе больше не создаёт операцию молча —
  открывается компактное подтверждение (сумма предзаполнена ожидаемой и выделена

- Операция создаётся с ВВЕДЁННОЙ суммой. Ожидаемый доход хранит обе величины:
  `amount` (ожидаемая, не перезаписывается) и `received_amount` (фактическая) +
  `linked_transaction_id`. Новые колонки добавлены миграцией.
- Если сумма изменена — в списке показывается «Получено X из Y».
- Для ежемесячных доходов правка касается только текущего месяца (строки
  материализованы помесячно, `amount` не трогается → следующий месяц ждёт исходную).

### Правила определения дубля (детерминированно, в копейках, без float)
- Отдельная тестируемая функция `findIncomeCandidates` (+ `moneyEqual`,
  `moneyWithinPct`, `daysApart`).
- Точное совпадение (категория + сумма до копейки + дата ±5 дней) и ровно один
  кандидат → автосвязь без создания операции, тост «Связано с доходом от …» +
  «Отменить» (5 сек).
- Похожее (±3%) либо несколько кандидатов → диалог «Похоже, этот доход уже внесён»
  со списком кандидатов + «Это новый доход».
- Отличие ≥ порога / нет кандидатов → создаётся новая операция.
- Уже связанные операции (`linked_transaction_id`) в поиске кандидатов исключаются;
  поиск ведётся по введённой сумме.
